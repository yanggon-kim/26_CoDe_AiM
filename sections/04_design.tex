\subsection{Overview: One Command, Many MAC Beats}
\label{sec:design:overview}

% P:des-tile-mac-overview
CoDe (Command-Decoupled PIM) issues one MAC command per weight column for a tile of $V$ token vectors of a skinny
GEMM, and this single \emph{tile MAC} command carries CoDe's two levers: row reuse (Section~\ref{sec:design:reuse})
and beat filling (Section~\ref{sec:design:beat}). Every command still obeys every DRAM timing parameter: activations,
column reads and refreshes issue exactly as in stock AiM, and only the MAC beats leave the command stream. Both levers
come from the tile, whose inputs the global buffer holds: CoDe extends the GB from stock AiM's one input vector to the
input vectors of $V$ tokens (Fig.~\ref{fig:tile}, Section~\ref{sec:design:pu}). Fig.~\ref{fig:tile} groups
the PU's structures by lever: the staging buffer, the accumulator file and the \emph{burst drain} carry row reuse, and the
weight latch and the beat sequencer carry beat filling. With both levers, CoDe's useful-MAC utilization $U$ reaches
0.779 on the mobile platform (Table~\ref{tab:umac}) and 0.739 on the edge server, against stock AiM's 0.179 and 0.193.

\subsection{Row Reuse}
\label{sec:design:reuse}

% P:des-row-reuse
Row reuse answers the non-MAC commands of Section~\ref{sec:bg:cmd}, whose row-switch commands stock AiM pays once per
token. Row reuse lets the $V$ tokens of a tile share one row sweep: the \emph{tile MAC}s (Table~\ref{tab:cmds}) sweep the open row's columns once for
all $V$ tokens, so the row-switch commands are paid once per $V$ tokens. Fig.~\ref{fig:mapping}a draws the tile in
GEMM terms at $M = V = 8$: the GB holds the eight tokens' inputs for one chunk of $K$, one bank's open 2\,KB row holds
one output's weights over that chunk, and the tile produces that output's eight sums. In Fig.~\ref{fig:mapping}b,
stock AiM sweeps the weight row once per token and pays a row switch and a drain in each of its eight sweeps, whereas
CoDe pays only one row switch for the tile; the row opens fall from eight to one and the column reads from 512 to 64. With $A$ tokens per row sweep, a token pays
$\trow / A + \ttok$ of non-MAC commands per row sweep, plus its share of refresh. The token load/drain commands stay
per token: WRGB writes each token's input chunk into the GB, and the \emph{burst drain} (Table~\ref{tab:cmds}) reads each token's sums once per row
sweep. The two families
of Section~\ref{sec:bg:walls} tie the tokens of a row sweep to one MAC slot ($A = 2$ and 4 in Table~\ref{tab:umac}),
whereas CoDe sets them by $V$ and leaves the PU's lanes unchanged. The non-MAC time per token thus falls
from stock AiM's 123.39\,ns to CoDe's 22.15\,ns at $V = 8$ on the mobile platform (Table~\ref{tab:umac}) and from
146.17 to 43.51\,ns at $V = 4$ on the edge server.

% P:des-reuse-novelty
Row reuse differs from the closest prior designs in how often a weight column is read. DOTS~\cite{dots} keeps a weight
row open across tokens but sweeps it once per token, with one MAC command and one column read per token on every
column, so the tile of Fig.~\ref{fig:mapping}b still costs 512 column reads. SAL-PIM~\cite{salpim} and the
Precision-Flexible PU~\cite{pfpu} spend several beats on one column read, but for one input vector, so each column is
still read once per token. CoDe's \emph{tile MAC} reads each column once and latches it beside the PU for all $V$
tokens, so the tile costs 64 column reads and 64 commands: each weight column is read once per tile of $V$ tokens
($V = 8$ on the mobile platform) instead of once per token. Each avoided column read saves its cell-access and
column-decoder energy, and against SAL-PIM and the Precision-Flexible PU, which sweep a row once per token, CoDe also
pays the row-switch commands once per tile. The latched column is what beat filling (Section~\ref{sec:design:beat})
spends in $D$ beats.

\subsection{Beat Filling}
\label{sec:design:beat}

% P:des-beat-decouple
Beat filling answers the idle beats of Section~\ref{sec:bg:cmd}, three of a stock MAC slot's four beats, by decoupling
the PU's MAC beats from the command stream. The PU runs its beats at its own clock, $f_\mathrm{PU} = D /
t_\mathrm{col}$, which equals CK on both platforms (Tables~\ref{tab:params} and~\ref{tab:designs}), so the PU fits $D$ beats into each column
period whatever the command spacing. A \emph{tile MAC} holds its column in the PU for $V/D$ column periods, and the next \emph{tile
MAC} issues $V/D$ periods later. The enlarged \emph{tile MAC} of Fig.~\ref{fig:mapping}b shows one tile of $V = 8$ tokens at
$D = 4$: one column read feeds eight beats, one per token and four per column period, and each beat adds into its
token's accumulator slot. The tile's partial sums leave in one \emph{burst drain} after its last column.

% P:des-beat-slot-factor
Beat filling raises the slot factor from stock AiM's 1/4 to 1, because every beat of a MAC slot computes for one token
of the tile. In the table of Fig.~\ref{fig:mapping}b, the weight row's time in MAC slots falls from 512
to 128 column periods for the same $8 \times 64$ MAC beats. With both levers joined, the weight row takes 738.75\,ns
against stock AiM's 3,250\,ns, 4.40$\times$ shorter, the speedup gap of Fig.~\ref{fig:mapping}b.

% P:des-beat-novelty
Beat filling differs from the two families of Section~\ref{sec:bg:walls} in what fills the beats of a column period.
LP-Spec~\cite{lpspec} keeps one MAC step per column command and widens the step: one column command feeds four 32-wide
ALUs with four tokens, so LP-Spec fills the beats with four times the multipliers. P3-LLM~\cite{p3llm} reuses a latched
column for two tokens, but each MAC still waits for its own command, issued only every \tccds, so one column read feeds
at most two tokens and the 8 tokens of Fig.~\ref{fig:timeline} read the column four times. CoDe starts its beats from
the PU clock instead: one \emph{tile MAC} command and one column read feed all $D$ beats of each column period over the
tile at the stock multiplier count, so the beats per column period follow $t_\mathrm{col} \times f_\mathrm{PU}$ rather
than the ratio of \tccdl{} to \tccds. Per token and weight column, CoDe therefore issues $1/V$ MAC commands, against
one for stock AiM and P3-LLM-style and $1/4$ for LP-Spec-style (Fig.~\ref{fig:timeline}). The idle beats thus
disappear without added multipliers, which gives CoDe 1.87$\times$ LP-Spec-style's tokens per second per logic
mm$^2$ on the mobile platform (Section~\ref{sec:eval:e2e}), and without per-token MAC commands, which gives CoDe its speed lead over
P3-LLM-style.

\subsection{Tile MAC Command and PU Microarchitecture}
\label{sec:design:pu}

% P:des-command-set
\runin{Command set}
CoDe adds two commands to the all-bank interface of AiM-style PIM~\cite{aimjssc} and keeps every other command
(Table~\ref{tab:cmds}). The \emph{tile MAC} (col, $V$) reads one column from every open bank with the stock MAC command's
timing and tells each PU to run $V$ beats on that column. The \emph{burst drain} moves a tile's $V$ sums out of every PU in
one burst after the tile's last column.


% P:des-tile-mac-pu
\runin{Tile MAC in the PU}
Fig.~\ref{fig:tile} follows one \emph{tile MAC} through the PU. The \emph{tile MAC} latches the column that the bank delivers in the
weight latch (\ding{172}). The beat sequencer then steps a token index $k$ from 0 to $V-1$, one beat per CK cycle
(\ding{173}). Beat $k$ multiplies the latched weights by token $k$'s slice from the staging buffer in the lanes (\ding{174}), and the adder
tree adds the products into accumulator slot $k$ (\ding{175}). After the tile's last column, the \emph{burst drain} moves the
$V$ sums out through the drain port (\ding{176}).

% P:des-storage
\runin{Storage}
The global buffer holds the tile's $V$ tokens for one chunk of $K$. On the mobile platform a $K$ chunk holds 2,048 INT8
inputs, 2\,KB per token, so the GB of an eight-token tile holds 16\,KB (Table~\ref{tab:designs}); one WRGB burst of 512
writes of 32\,B fills it. The staging buffer next to the lanes is a three-entry queue of 512-bit GB words, each word
packing two tokens' slices, and a register of $V$ slices on HBM2. The accumulator file holds two sets of $V$ slots per bank, so
one tile's sums drain from one set while the next tile accumulates into the other; an HBM2 PU, which serves two banks,
holds four sets (Table~\ref{tab:designs}).

% P:des-tile-size
\runin{Tile size}
The tile size $V$ sizes CoDe's GB, HBM2 staging register and accumulator file, while the lanes, the weight latch, the
beat sequencer and the mobile staging queue keep their size at any $V$. Below $V = D$ the column period paces the PU and beats idle; from
$V = D$ every beat computes, and a larger $V$ cuts only the row-switch term $\trow / V$ of a token's non-MAC time. A weight row takes $\lceil M/V \rceil$ row sweeps, so a last sweep with fewer than $V$
tokens, or any $V > M$, leaves slots idle, and $V$ is sized for the range of $M$ a platform serves. CoDe sets
$V = 2D = 8$ on the mobile platform and $V = D = 4$ on HBM2; Section~\ref{sec:eval:ablation} explains how $V$ is chosen.

% P:des-pu-clock
\runin{PU clock}
CoDe needs a PU clock above the column rate, not one equal to CK, and the tile keeps that clock within the reach of
the DRAM silicon of Section~\ref{sec:bg:depth}. Registered stages pipeline each beat (latch and staging
operands, multiply, adder tree, accumulate); only the accumulate feeds back, and beat $k$ writes accumulator slot $k$, so each slot takes one update per tile of $V \ge D$ beats, and the add loop of each slot spans a column
period or more. CoDe's lanes multiply integers, INT8 on the mobile platform and INT4\,$\times$\,INT8 on HBM2,
narrower operands than the BF16 of that section's 1\,GHz multipliers.
Synthesized with Synopsys Design Compiler on a 14\,nm library (Section~\ref{sec:method:models}), the pipelined PU meets
timing at 0.8\,GHz on the mobile platform and at 1\,GHz on HBM2, as PrimeTime confirms.
