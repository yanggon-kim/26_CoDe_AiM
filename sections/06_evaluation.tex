\section{Evaluation}
\label{sec:eval}

% P:eval-modelled
All results are modelled, and ratios above 1 favour CoDe. Three modelling choices favour the rivals: LP-Spec-style
keeps only the accumulators its dataflow needs (Section~\ref{sec:bg:walls}) and runs one unit per bank on the mobile platform, faster than
LP-Spec's shared unit, and P3-LLM-style gains more from depth 2 than P3-LLM reports
(Section~\ref{sec:method:models}).

\subsection{Skinny GEMM Speedup and Area Efficiency}
\label{sec:eval:gemm}

% P:eval-gemm-summary
CoDe reaches LP-Spec-style's GEMM speed on under three fifths of its logic, and exceeds P3-LLM-style's speed beyond
two token rows.

% P:eval-gemm-per-mm2
\runin{GEMM throughput per logic mm$^2$}
Per logic mm$^2$, CoDe leads LP-Spec-style's GEMM throughput on both platforms. CoDe fills the same beats as
LP-Spec-style but spends its logic on storage rather than multipliers, so CoDe runs at least as fast as LP-Spec-style with
0.574$\times$ its logic area on the mobile platform and 0.554$\times$ on the edge server
(Table~\ref{tab:designs}; Section~\ref{sec:eval:area}). CoDe therefore returns 1.74$\times$ LP-Spec-style's GEMM throughput per logic
mm$^2$ on the mobile platform up to $M = 4$ and 1.94$\times$ from $M = 8$; on the edge server the ratio is
1.80$\times$ at every $M$ (Fig.~\ref{fig:gemm}b). Against P3-LLM-style, CoDe's speed outgrows its larger logic
beyond $M = 2$: CoDe returns 1.35$\times$ P3-LLM-style's throughput per logic mm$^2$ at $M = 4$ and 1.50--1.51$\times$ from
$M = 8$ on the mobile platform, and 1.44--1.45$\times$ from $M = 4$ on the edge server. Only at $M \le 2$, where CoDe's
third and fourth beats sit idle, does P3-LLM-style's smaller PU lead, with CoDe at 0.71$\times$ on the mobile platform
and 0.74--0.75$\times$ on the edge server.

% P:eval-gemm-speed
\runin{GEMM speed}
Up to $M = 2$ the column period paces every design: one column read serves every token, and CoDe,
LP-Spec-style and P3-LLM-style all run 1.96--1.97$\times$ faster than stock AiM at $M = 2$ (Fig.~\ref{fig:gemm}a). Beyond
$M = 2$ P3-LLM-style needs a second pass for the tokens beyond its two per read, while CoDe fills up to four beats per
command: at $M = D = 4$ CoDe runs 3.74$\times$ stock AiM's speed on the mobile platform and 3.82$\times$ on the edge
server, against P3-LLM-style's 1.95$\times$, and at $M = 64$ CoDe runs 4.16$\times$ and 3.80$\times$. Filling LP-Spec-style's four beats per column period,
CoDe equals LP-Spec-style's speed up to $M = 4$, and at every $M$ on the edge
server, where CoDe's tile of $V = D = 4$ issues LP-Spec-style's command stream. On the mobile platform CoDe runs ahead
of LP-Spec-style from $M = 8$, because its eight-token tile halves LP-Spec-style's row sweeps.

\subsection{End-to-End Speedup and Area Efficiency}
\label{sec:eval:e2e}

% P:eval-e2e-overview
Fig.~\ref{fig:e2e} runs whole decoding on the five systems at the operating points of Section~\ref{sec:method:work}:
the speculative loop at $M = 8$ on the mobile platform and a batch of 8 on the edge server. CoDe decodes
3.22$\times$ faster than NPU only on the mobile platform, at 29.9 tokens/s, and 1.28$\times$ faster on the edge server,
at 456 tokens/s, where stock AiM reaches 1.27$\times$ and 0.45$\times$ (Fig.~\ref{fig:e2e}a).

% P:eval-e2e-lpspec
\runin{Area efficiency against LP-Spec-style}
CoDe returns 1.87$\times$ LP-Spec-style's tokens per second per logic mm$^2$ on the mobile platform and 1.80$\times$ on
the edge server (Fig.~\ref{fig:e2e}b), because CoDe decodes at least as fast on less logic. On the mobile
platform LP-Spec-style reaches 3.00$\times$ NPU only's speed, at 27.9 tokens/s, so CoDe decodes 1.07$\times$ faster on
0.574$\times$ its logic. The lead holds at every $M$: across $M = 2$--16, CoDe decodes at least as fast as
LP-Spec-style and returns 1.75--2.28$\times$ its tokens per second per logic mm$^2$. On the edge server, CoDe matches LP-Spec-style's speed on 0.554$\times$ its logic. CoDe keeps its lead per logic
mm$^2$ over LP-Spec-style until storage costs 6.5$\times$ our estimate on the mobile platform and 16.5$\times$ on the
edge server.

% P:eval-lpspec-variants
\runin{Cost of a faster LP-Spec-style}
The eight-token tile is what decoupling makes affordable. An eight-token LP-Spec-style design matches CoDe's loop speed
at every $M$ we run (2--4, 8 and 16) and its GEMM speed from $M = 8$ (CoDe 1.007$\times$ at $M = 12$), but grows its
logic per die from LP-Spec-style's 2.800 to 3.155\,mm$^2$ (Table~\ref{tab:designs}), so CoDe returns 1.96$\times$ its tokens per second per logic mm$^2$. The tile thus gives
CoDe its speed lead over the per-bank LP-Spec-style, at $M = 8$ and 16, and CoDe's tile costs storage, not multipliers.

% P:eval-e2e-p3
\runin{Speed against P3-LLM-style}
CoDe decodes a batch of 8 1.41$\times$ faster than P3-LLM-style on the edge server, where P3-LLM-style runs at
0.91$\times$ NPU only's speed (Fig.~\ref{fig:e2e}a). P3-LLM-style here follows P3-LLM's own placement, with the linear
layers on the NPU and attention on PIM, while CoDe keeps every layer on PIM, its fastest placement at this batch. On
the mobile platform P3-LLM-style reaches 2.06$\times$ NPU only's speed, because its two-token read needs four passes
over the eight token rows. CoDe's speed lead more than repays its larger logic: CoDe returns 1.11$\times$
P3-LLM-style's decoding throughput per logic mm$^2$ on the mobile platform and 1.05$\times$ on the edge server,
although the metric charges P3-LLM-style no area for the linear layers it runs on the NPU.

\subsection{Energy and Peak Power}
\label{sec:eval:energy}

% P:eval-energy
\runin{Energy per token}
CoDe spends the least energy per token of the five systems on the mobile platform and ties for the least on the edge
server. On the mobile platform CoDe spends 105.8\,mJ per token at $M = 8$, while NPU only spends 6.0$\times$, stock AiM 1.96$\times$,
P3-LLM-style 1.40$\times$ and LP-Spec-style 1.14$\times$ CoDe's energy (Fig.~\ref{fig:e2e}c). On the edge server,
with the NPU idling at 55\,W while the PIM works, CoDe spends 145\,mJ per token. NPU only spends
1.48$\times$, stock AiM 2.73$\times$ and P3-LLM-style 1.52$\times$ CoDe's energy, and CoDe matches LP-Spec-style's energy. With the idle NPU
power-gated, P3-LLM-style's ratio grows to 2.08$\times$: CoDe is fast enough to keep the linear layers in the banks,
while P3-LLM-style's NPU must read every linear-layer weight over the HBM pins, which accounts for 76\,\% of the gap.

% P:eval-power-headroom
\runin{Power headroom of all-bank PIM}
A stock DRAM die holds its banks to a tight current limit: its \tfaw{} window admits only four row activations because
the die's charge pumps and their power-delivery network supply only that current~\cite{shevgoor}. PIM dies lift this
limit so that all their banks can work at once. GDDR6-AiM's~\cite{aimjssc} all-bank MACs draw about three times the
gapless read current, and reservoir capacitors and separate I/O and bank power networks let its 16 banks activate
together without \tfaw. AttAcc~\cite{attacc} budgets its GEMV units by the all-bank interleaved read current (IDD7),
Newton's~\cite{newton} authors estimate that its all-bank computation draws about 4$\times$ the power of a peak-bandwidth
read. CoDe's design operates within this headroom.

% P:eval-power
\runin{Peak power}
CoDe's peak power falls inside this headroom on both platforms and stays close to LP-Spec-style's. CoDe draws
0.54\,W per die at its full MAC rate, 1.20$\times$ the power of one x16 channel reading at its full
rate (Section~\ref{sec:method:models}), below the threefold read current of AiM's MACs. On HBM2, CoDe draws
5.98\,W per stack, 0.75$\times$ the stack's full-rate read power; HBM-PIM~\cite{hbmpim} likewise keeps its PIM mode within the thermal design power of the original
HBM system. CoDe draws 0.92$\times$ LP-Spec-style's peak power on the mobile platform and 0.87$\times$ on HBM2, and
without its clock gates 1.04$\times$ and 1.03$\times$ LP-Spec-style's peak
(Table~\ref{tab:designs}). CoDe spreads its MAC rate over four times as many clock edges as LP-Spec-style,
so each CoDe edge draws 3.4$\times$ less charge on the mobile platform and 3.1$\times$ less on HBM2.

\subsection{Area Against Silicon Budgets}
\label{sec:eval:area}

% P:eval-area-budget
Fabricated PIM dies set the scale for a PIM design's logic area, which a DRAM die pays for in memory capacity
(Section~\ref{sec:bg:walls}). Samsung's HBM-PIM~\cite{hbmpim} places 32 PIM units
of 0.712\,mm$^2$ each on an 84.4\,mm$^2$ die, 27\,\% of the die by our division; GDDR6-AiM's~\cite{aimjssc} compute circuits take 20--25\,\% of its chip (Section~\ref{sec:bg:walls}). CoDe's logic (Table~\ref{tab:designs}) takes
2.64\,\% of the LPDDR5 die and 2.28\,\% of the HBM2 stack, against AiM's 20--25\,\%. Like AiM, CoDe keeps every cell array and places its PUs in the bank
periphery.

% P:eval-area-split
\runin{Logic against LP-Spec-style}
CoDe matches LP-Spec-style's peak throughput on the mobile platform with 0.574$\times$ its logic area per die: arithmetic takes
0.71 of LP-Spec-style's logic and 0.31 of CoDe's, while storage, the staging queue, accumulator file and weight latch,
takes 0.39 of CoDe's logic and 0.14 of LP-Spec-style's. CoDe does not pay for the saved area with power: its peak power
stays below LP-Spec-style's on both platforms (Section~\ref{sec:eval:energy}). On HBM2, CoDe's logic is 0.554$\times$ LP-Spec-style's and
1.35$\times$ P3-LLM-style's, an area that buys twice P3-LLM-style's beats per column period.

\runin{Sources of CoDe's gain}
CoDe's gain over stock AiM has two sources, row reuse and beat filling. Table~\ref{tab:umac_src} adds the two sources with row reuse first for one decoder layer's weight GEMMs at $M = 8$, the layer of Table~\ref{tab:umac} on the mobile platform. The row-reuse-only design keeps the stock PU's pace of one beat per column
period and adds CoDe's storage and row sweeps of $V$ tokens; we simulate it as CoDe's trace at $D = 1$, which reads
each weight column of the layer once, as CoDe does: one eighth as often as stock AiM, a quarter as often as
P3-LLM-style and half as often as LP-Spec-style. Row reuse alone speeds
the layer up 1.24$\times$ on the mobile platform and 1.15$\times$ on the edge server, yet $U$ reaches 0.223 and
0.222, because \UMAC stays at 1/4. Beat filling then adds one beat per column period at each step, raising \UMAC to
0.50, 0.73 and 1.00, and its three steps
speed the layer up 3.49$\times$ on the mobile platform and 3.33$\times$ on the edge server, while CoDe's \fMAC of 0.779 and 0.739 stays
near stock AiM's 0.717 and 0.771. End to end, beat filling makes CoDe decode 2.03$\times$ faster than row reuse alone
in the speculative loop at $M = 8$ on the mobile platform and 2.29$\times$ faster at a batch of 8 on the edge server. At $D = 2$, half its PU clock, CoDe already returns 1.07$\times$
LP-Spec-style's throughput per logic mm$^2$ on this layer on the mobile platform and 1.015$\times$ on the edge server,
because its logic is the same at every $D$.
Beat filling pays off only after row reuse. Applied alone, it would shorten every MAC slot to a quarter but keep every
row-switch command, which would then take about half of the time or more (\fMAC 0.425 on the mobile platform and 0.506
on the edge server).

% P:eval-vsweep-gain
\runin{Tile size on a full GEMM}
Fig.~\ref{fig:vsweep}a sweeps the tile size $V$ from 1 to 64 for q\_proj at $M = 64$, where every tile is full. With $D = 4$ PU beats per column period (Section~\ref{sec:bg:pim}), up to $V = D$ a larger
tile fills idle beats, and beyond
$V = D$ it removes only row-switch commands. CoDe's q\_proj speed-up over stock AiM rises from 1 at $V = 1$ to
3.86$\times$ on the mobile platform and 3.69$\times$ on the edge server at $V = D$, but only to 4.90$\times$ and
4.39$\times$ at $V = 64$. On the mobile platform idle beats supply 72\,\% of the time saved from $V = 1$ to 2, and
row-switch commands 91.6\,\% of that from $V = 4$ to 8.

% P:eval-vsweep-area
Past $V = D$ ($D = 4$) CoDe's storage grows faster than its speed. From $V = 4$ to 8 CoDe's logic grows by 19\,\% on the
mobile platform and by 45\,\% on the edge server, while its speed grows 1.117$\times$ and 1.089$\times$, so
throughput per logic mm$^2$ peaks at $V = D$ on both platforms, at 2.89$\times$ and 2.28$\times$ stock AiM's, and falls to 1.51$\times$ and 0.34$\times$ at $V = 64$
(Fig.~\ref{fig:vsweep}a). A full tile thus favours $V = D$, but a decode step runs at small $M$, where the last row
sweep of a tile is often only partly filled.

% P:eval-vsweep-choice
\runin{Tile size across {\boldmath$M$}}
CoDe uses $V = 8$ on the mobile platform and $V = 4$ on the edge server, the tile size that loses least in its worst
case across $M = 3$--16. Fig.~\ref{fig:vsweep}b divides $V = 8$'s decode-step throughput per logic mm$^2$ by $V = 4$'s. On the
mobile platform, $V = 8$ wins where it saves $V = 4$ a partly filled row sweep, at $M = 5$--7, 9--10 and 13--14
(1.290$\times$ at $M = 5$), and loses at $M \le 4$, where both tiles run one row sweep (0.840$\times$); against the
best $V$ at each $M$, $V = 8$ loses at most 16.0\,\%, while $V = 4$ loses 27.5\,\% on q\_proj. On the edge server, $V = 8$ never
breaks even (0.690--0.915$\times$), and $V = 4$ loses at most 8.9\,\% against $V = 8$'s 31.0--32.2\,\%.
