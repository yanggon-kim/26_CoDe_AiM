\section{Evaluation}
\label{sec:eval}

% P:eval-modelled
All results are modelled, and ratios above 1 favour CoDe. Three modelling choices favour the rivals: LP-Spec-style
keeps only the accumulators its dataflow needs (Section~\ref{sec:bg:walls}) and runs one unit per bank on the mobile platform, faster than
LP-Spec's shared unit (Section~\ref{sec:eval:ablation}), and P3-LLM-style gains more from depth 2 than P3-LLM reports
(Section~\ref{sec:method:models}).

\subsection{Skinny GEMM Speedup and Area Efficiency}
\label{sec:eval:gemm}

% P:eval-gemm-summary
CoDe runs GEMMs at least as fast as LP-Spec-style on about half its logic, and faster than P3-LLM-style once a GEMM
has more than two token rows.

% P:eval-gemm-speed
\paragraph{GEMM speed}
Up to $M = 2$ the column period paces every design: one column read serves every token, and CoDe,
LP-Spec-style and P3-LLM-style all run 1.96--1.97$\times$ faster than stock AiM at $M = 2$ (Fig.~\ref{fig:gemm}a). Beyond
$M = 2$ P3-LLM-style needs a second pass for the tokens beyond its two per read, while CoDe fills up to four beats per
command: at $M = D = 4$ CoDe runs 3.74$\times$ stock AiM's speed on the mobile platform and 3.82$\times$ on the edge
server, against P3-LLM-style's 1.95$\times$, and at $M = 64$ CoDe runs 4.16$\times$ and 3.80$\times$. CoDe fills the same four beats per column period that LP-Spec-style
fills with four times the multipliers, so CoDe equals LP-Spec-style's speed up to $M = 4$, and at every $M$ on the edge
server, where CoDe's tile of $V = D = 4$ issues LP-Spec-style's command stream. On the mobile platform CoDe runs ahead
of LP-Spec-style from $M = 8$, because its eight-token tile halves LP-Spec-style's row sweeps.

% P:eval-gemm-per-mm2
\paragraph{GEMM throughput per logic mm$^2$}
Per logic mm$^2$, CoDe nearly doubles LP-Spec-style's GEMM throughput on both platforms. CoDe fills the same beats as
LP-Spec-style but spends its logic on storage rather than multipliers, so CoDe runs at least as fast as LP-Spec-style with
0.539$\times$ its logic area on the mobile platform and 0.56$\times$ on the edge server
(Table~\ref{tab:designs}; Section~\ref{sec:eval:area}). CoDe therefore returns 1.86$\times$ LP-Spec-style's GEMM throughput per logic
mm$^2$ on the mobile platform up to $M = 4$ and 2.07$\times$ from $M = 8$; on the edge server the ratio is
1.79$\times$ at every $M$ (Fig.~\ref{fig:gemm}b). Against P3-LLM-style, CoDe's speed outgrows its larger logic
beyond $M = 2$: CoDe returns 1.43$\times$ P3-LLM-style's throughput per logic mm$^2$ at $M = 4$ and 1.59$\times$ from
$M = 8$ on the mobile platform, and 1.46--1.47$\times$ from $M = 4$ on the edge server. Only at $M \le 2$, where CoDe's
third and fourth beats sit idle, does P3-LLM-style's smaller PU lead, with CoDe at 0.75$\times$.

\subsection{End-to-End Speedup and Area Efficiency}
\label{sec:eval:e2e}

% P:eval-e2e-phone
\paragraph{Mobile platform}
Fig.~\ref{fig:e2e} runs whole decoding on the five systems of Section~\ref{sec:method:work}: the speculative loop at
$M = 4$ on the mobile platform and a batch of 8 on the edge server. At acceptance rate 0.7 a round of the loop yields
fewer than $1/(1 - 0.7) \approx 3.3$ tokens on average, and $M = 4$ is NPU only's
best $M$ and within 2\,\% of NPU + CoDe's and NPU + LP-Spec-style's best throughput; a batch of 8 is a light edge-server
load. On the mobile platform CoDe
decodes fastest, 4.37$\times$ faster than NPU only at 46.4 tokens/s, ahead of LP-Spec-style's 4.34$\times$ at 46.1
(Fig.~\ref{fig:e2e}a). P3-LLM-style reaches 2.96$\times$, because its two-token read needs two passes over the four
token rows, and stock AiM reaches 1.81$\times$. At each system's own best $M$ the order holds: CoDe reaches
47.1 tokens/s and LP-Spec-style 46.8 at $M = 3$, P3-LLM-style 43.8 and stock AiM 26.5 at $M = 2$, and NPU only 10.6
at $M = 4$.

% P:eval-e2e-server
\paragraph{Edge server}
On the edge server CoDe decodes a batch of 8 1.28$\times$ faster than NPU only, at 456 tokens/s, and matches
LP-Spec-style's speed on 0.56$\times$ its logic (Fig.~\ref{fig:e2e}a). Stock AiM runs at 0.45$\times$ and P3-LLM-style at 0.76$\times$ NPU only's speed,
so CoDe decodes 1.68$\times$ faster than P3-LLM-style. On the five-model geometric mean, NPU only overtakes CoDe from batch 16.

% P:eval-e2e-per-mm2
\paragraph{Throughput per logic mm$^2$}
CoDe decodes at least as fast as LP-Spec-style on about half its logic, so CoDe returns 1.87$\times$ LP-Spec-style's tokens per second per logic mm$^2$ on the
mobile platform and 1.79$\times$ on the edge server (Fig.~\ref{fig:e2e}b). Against P3-LLM-style, CoDe's speed lead more than repays its larger logic:
CoDe returns 1.10$\times$ P3-LLM-style's decoding throughput per logic mm$^2$ on the mobile platform and 1.26$\times$ on the
edge server.

% P:eval-lpspec-variants
\paragraph{Eight-token LP-Spec-style}
An eight-token tile does not close CoDe's lead per logic mm$^2$ on the mobile platform. CoDe matches the eight-token LP-Spec-style's
loop speed at every $M$ we run (2--4, 8 and 16) and its GEMM speed from $M = 8$ (1.007$\times$ at $M = 12$),
so the tile, not decoupling, gives CoDe its mobile speed lead over the per-bank LP-Spec-style beyond $M = 4$. The
eight-token tile, however, grows LP-Spec-style's logic to 4.72\,\% of the die, and CoDe returns 2.05$\times$ that
design's tokens per second per logic mm$^2$.

\subsection{Energy and Peak Power}
\label{sec:eval:energy}

% P:eval-energy
\paragraph{Energy per token}
CoDe spends the least energy per token of the five systems on the mobile platform and ties for the least on the edge
server. On the mobile platform CoDe spends 70.5\,mJ per token at $M = 4$, while NPU only spends 7.9$\times$, stock AiM 1.80$\times$,
P3-LLM-style 1.28$\times$ and LP-Spec-style 1.04$\times$ CoDe's energy (Fig.~\ref{fig:e2e}c). On the edge server,
with the NPU idling at 55\,W while the PIM works, CoDe spends 145\,mJ per token. NPU only spends
1.48$\times$, stock AiM 2.73$\times$ and P3-LLM-style 1.64$\times$ CoDe's energy, and CoDe matches LP-Spec-style's energy; with the idle NPU power-gated, P3-LLM-style spends 1.46$\times$
CoDe's energy.

% P:eval-power-headroom
\paragraph{Power headroom of all-bank PIM}
A stock DRAM die holds its banks to a tight current limit: its \tfaw{} window admits only four row activations because
the die's charge pumps and their power-delivery network supply only that current~\cite{shevgoor}. PIM dies lift this
limit so that all their banks can work at once. GDDR6-AiM's~\cite{aimjssc} all-bank MACs draw about three times the
gapless read current, and reservoir capacitors and separate I/O and bank power networks let its 16 banks activate
together without \tfaw. AttAcc~\cite{attacc} budgets its GEMV units by the all-bank interleaved read current (IDD7),
Newton's~\cite{newton} authors estimate that its all-bank computation draws about 4$\times$ the power of a peak-bandwidth
read. CoDe's design operates within this headroom.

% P:eval-power
\paragraph{Peak power}
CoDe's peak power falls inside this headroom on both platforms and stays close to LP-Spec-style's. CoDe draws
0.54\,W per die at its full MAC rate, 1.20$\times$ the power of one x16 channel reading at its full
rate (Section~\ref{sec:method:models}), below the threefold read current of AiM's MACs. On HBM2, CoDe draws
5.98\,W per stack, 0.75$\times$ the stack's full-rate read power; HBM-PIM~\cite{hbmpim} likewise keeps its PIM mode within the thermal design power of the original
HBM system. CoDe draws 0.92$\times$ LP-Spec-style's peak power on the mobile platform and 0.87$\times$ on HBM2, and
without its clock gates 1.04$\times$ and 1.03$\times$ LP-Spec-style's peak
(Table~\ref{tab:designs}). CoDe spreads its MAC rate over four times as many clock edges as LP-Spec-style,
so each CoDe edge draws 3.4$\times$ less charge on the mobile platform and 3.1$\times$ less on HBM2.

\subsection{Area Against Silicon Budgets}
\label{sec:eval:area}

% P:eval-area-budget
Fabricated PIM dies set the scale for a PIM design's logic area, which a DRAM die pays for in memory capacity
(Section~\ref{sec:bg:walls}). Samsung's HBM-PIM~\cite{hbmpim} places 32 PIM units
of 0.712\,mm$^2$ each on an 84.4\,mm$^2$ die, 27\,\% of the die by our division; GDDR6-AiM's compute circuits take 20--25\,\% of its chip (Section~\ref{sec:bg:walls}). CoDe's logic (Table~\ref{tab:designs}) takes
2.31\,\% of the LPDDR5 die and 1.95\,\% of the HBM2 stack, and 4.96\,\% and 4.02\,\% at AiM's
silicon scale, at most a quarter of AiM's share. Like AiM, CoDe keeps every cell array and places its PUs in the bank
periphery.

% P:eval-area-split
\paragraph{Logic against LP-Spec-style}
CoDe matches LP-Spec-style's peak throughput on the mobile platform with 0.539$\times$ its logic area per die: arithmetic takes
0.73 of LP-Spec-style's logic and 0.34 of CoDe's, while storage, the staging queue, accumulator file and weight latch,
takes 0.32 of CoDe's logic and 0.10 of LP-Spec-style's. On HBM2, CoDe's logic is 0.56$\times$ LP-Spec-style's and
1.33$\times$ P3-LLM-style's, an area that buys twice P3-LLM-style's beats per column period.

\subsection{Ablation Study}
\label{sec:eval:ablation}

% P:eval-gain-sources
\paragraph{Sources of CoDe's gain}
CoDe's gain over stock AiM has two sources, row reuse and beat filling. Table~\ref{tab:umac_src} adds the two sources with row reuse first for one decoder layer's weight GEMMs at $M = 8$, the layer of Table~\ref{tab:umac} on the mobile platform. The row-reuse-only design keeps the stock PU's pace of one beat per column
period and adds CoDe's storage and row sweeps of $V$ tokens; we simulate it as CoDe's trace at $D = 1$. Row reuse alone speeds
the layer up 1.24$\times$ on the mobile platform and 1.15$\times$ on the edge server, yet $U$ reaches 0.223 and
0.222, because \UMAC stays at 1/4. Beat filling then adds one beat per column period at each step, raising \UMAC to
0.50, 0.73 and 1.00 ($D = 3$ runs 2.91 beats, as the PU's hold rounds to whole simulator cycles), and its three steps
speed the layer up 3.49$\times$ on the mobile platform and 3.33$\times$ on the edge server, while CoDe's \fMAC of 0.779 and 0.739 stays
near stock AiM's 0.717 and 0.771. At $D = 2$, half its PU clock, CoDe already returns 1.14$\times$
LP-Spec-style's throughput per logic mm$^2$ on this layer on the mobile platform and 1.02$\times$ on the edge server,
because its logic changes by at most 1.3\,\% across $D$.
Beat filling pays off only after row reuse. Applied alone, it would shorten every MAC slot to a quarter but keep every
row-switch command, which would then take about half of the time or more (\fMAC 0.425 on the mobile platform and 0.506
on the edge server).

% P:eval-vsweep-gain
\paragraph{Tile size on a full GEMM}
Fig.~\ref{fig:vsweep}a sweeps the tile size $V$ from 1 to 64 for q\_proj at $M = 64$, where every tile is full. Up to $V = D$ a larger tile fills idle beats, and beyond
$V = D$ it removes only row-switch commands. CoDe's q\_proj speed-up over stock AiM rises from 1 at $V = 1$ to
3.86$\times$ on the mobile platform and 3.69$\times$ on the edge server at $V = D$, but only to 4.90$\times$ and
4.39$\times$ at $V = 64$. On the mobile platform idle beats supply 72\,\% of the time saved from $V = 1$ to 2, and
row-switch commands 91.6\,\% of that from $V = 4$ to 8.

% P:eval-vsweep-area
Past $V = D$ CoDe's storage grows faster than its speed. From $V = 4$ to 8 CoDe's logic grows by 16\,\% on the
mobile platform and by 40\,\% on the edge server, while its speed grows 1.117$\times$ and 1.089$\times$, so
throughput per logic mm$^2$ peaks at $V = D$ on both platforms, at 3.01$\times$ and 2.34$\times$ stock AiM's, and falls to 1.66$\times$ and 0.38$\times$ at $V = 64$
(Fig.~\ref{fig:vsweep}a). A full tile thus favours $V = D$, but a decode step runs at small $M$, where the last row
sweep of a tile is often only partly filled.

% P:eval-vsweep-choice
\paragraph{Tile size across $M$}
CoDe uses $V = 8$ on the mobile platform and $V = 4$ on the edge server, the tile size that loses least in its worst
case across $M = 3$--16, because a decode step runs at small $M$, where a larger tile often leaves its last row sweep
partly filled. Fig.~\ref{fig:vsweep}b divides $V = 8$'s decode-step throughput per logic mm$^2$ by $V = 4$'s. On the
mobile platform, $V = 8$ wins where it saves $V = 4$ a partly filled row sweep, at $M = 5$--7, 9--10 and 13--15
(1.324$\times$ at $M = 5$), and loses at $M \le 4$, where both tiles run one row sweep (0.862$\times$); against the
best $V$ at each $M$, $V = 8$ loses at most 13.8\,\%, while $V = 4$ loses 29.4\,\% on q\_proj. On the edge server, $V = 8$ never
breaks even (0.712--0.944$\times$), and $V = 4$ loses at most 11.7\,\% against $V = 8$'s 28.8--30.0\,\%.

% P:eval-placement
\paragraph{PU placement}
CoDe keeps its lead under the other placement commercial PIM uses, one unit shared between two banks
(Section~\ref{sec:bg:pim}). Sharing costs speed only when a bank delivers a column as often as a unit can take one. On the
edge server, a bank delivers a column every 8\,ns and a PU takes one every 4\,ns (Table~\ref{tab:params}), so every design
there, CoDe included, already shares one PU between two banks at full speed. On the mobile platform, a bank delivers a
column every 5\,ns, as fast as a unit takes one, so a shared unit halves each bank's rate. Built with one unit per two
banks, as LP-Spec~\cite{lpspec} publishes it, LP-Spec-style takes 0.96$\times$ CoDe's logic, and CoDe decodes
1.49$\times$ faster at $M = 4$ and returns 1.42$\times$ its tokens per second per logic mm$^2$. Whichever placement
LP-Spec-style uses, CoDe therefore decodes at least as fast and returns more throughput per logic mm$^2$.
