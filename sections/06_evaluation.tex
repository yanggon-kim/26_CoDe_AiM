\section{Evaluation}
\label{sec:eval}

% P:eval-modelled
All results are modelled, and ratios above 1 favour CoDe. We judge CoDe against each family by the cost that defines
it: against LP-Spec-style, which buys speed with multipliers, by throughput per logic mm$^2$, and against P3-LLM-style,
which keeps the stock multipliers but caps speed, by speed. Three modelling choices of
Sections~\ref{sec:bg:walls} and~\ref{sec:method:models} favour the rivals: LP-Spec-style's minimal accumulators and
per-bank unit, and P3-LLM-style's depth-2 gain.

\subsection{Skinny GEMM Speedup and Area Efficiency}
\label{sec:eval:gemm}

% P:eval-gemm-summary
CoDe reaches LP-Spec-style's GEMM speed on under three fifths of its logic, and exceeds P3-LLM-style's speed beyond
two token rows.

% P:eval-gemm-setting
Up to $M = 2$ the column period paces every design: one column read serves every token, and CoDe,
LP-Spec-style and P3-LLM-style all run 1.96--1.97$\times$ faster than stock AiM at $M = 2$ (Fig.~\ref{fig:gemm}a).

% P:eval-gemm-lpspec
\runin{Area efficiency against LP-Spec-style}
CoDe returns 1.74$\times$ LP-Spec-style's GEMM throughput per logic mm$^2$ on the mobile platform up to $M = 4$ and
1.94$\times$ from $M = 8$, and 1.80$\times$ at every $M$ on the edge server (Fig.~\ref{fig:gemm}b). CoDe fills the same
beats as LP-Spec-style but spends its logic on storage rather than multipliers (Section~\ref{sec:eval:area}). CoDe equals LP-Spec-style's speed up to $M = 4$, and at every
$M$ on the edge server, where CoDe's tile of $V = D = 4$ issues LP-Spec-style's command stream. On the mobile platform
CoDe runs ahead of LP-Spec-style from $M = 8$, because its eight-token tile halves LP-Spec-style's row sweeps.

% P:eval-gemm-p3
\runin{Speed against P3-LLM-style}
Beyond $M = 2$ P3-LLM-style needs a second pass for the tokens beyond its two per read, while CoDe fills up to four
beats per command: at $M = D = 4$ CoDe runs 3.74$\times$ stock AiM's speed on the mobile platform and 3.82$\times$ on
the edge server, against P3-LLM-style's 1.95$\times$, and at $M = 64$ CoDe runs 4.16$\times$ and 3.80$\times$
(Fig.~\ref{fig:gemm}a). CoDe's speed outgrows its larger logic beyond $M = 2$: CoDe returns 1.35$\times$
P3-LLM-style's throughput per logic mm$^2$ at $M = 4$ and 1.50--1.51$\times$ from $M = 8$ on the mobile platform, and
1.44--1.45$\times$ from $M = 4$ on the edge server; P3-LLM-style's smaller PU leads only at $M \le 2$, where CoDe's
third and fourth beats sit idle (0.71$\times$ and 0.74--0.75$\times$).

\subsection{End-to-End Speedup and Area Efficiency}
\label{sec:eval:e2e}

% P:eval-e2e-overview
Fig.~\ref{fig:e2e} runs whole decoding on the five systems at the operating points of Section~\ref{sec:method:work}:
the speculative loop at $M = 8$ on the mobile platform and a batch of 8 on the edge server. CoDe decodes
3.22$\times$ faster than NPU only on the mobile platform, at 29.9 tokens/s, and 1.28$\times$ faster on the edge server,
at 456 tokens/s, where stock AiM reaches 1.27$\times$ and 0.45$\times$ (Fig.~\ref{fig:e2e}a).

% P:eval-e2e-lpspec
\runin{Area efficiency against LP-Spec-style}
CoDe returns 1.87$\times$ LP-Spec-style's tokens per second per logic mm$^2$ on the mobile platform and 1.80$\times$ on
the edge server (Fig.~\ref{fig:e2e}b), because CoDe decodes at least as fast on less logic. On the mobile
platform LP-Spec-style reaches 3.00$\times$ NPU only's speed, at 27.9 tokens/s, so CoDe decodes 1.07$\times$ faster on
0.574$\times$ its logic. The lead holds at every $M$: across $M = 2$--16, CoDe decodes at least as fast as
LP-Spec-style and returns 1.75--2.28$\times$ its tokens per second per logic mm$^2$. An eight-token LP-Spec-style design matches
CoDe's speed but needs 3.155\,mm$^2$ of logic per die, so CoDe returns 1.96$\times$ its tokens per second per logic
mm$^2$. On the edge server, CoDe matches LP-Spec-style's speed on 0.554$\times$ its logic. CoDe keeps its lead per logic
mm$^2$ over LP-Spec-style until storage costs 6.5$\times$ our estimate on the mobile platform and 16.5$\times$ on the
edge server.

% P:eval-e2e-p3
\runin{Speed against P3-LLM-style}
CoDe decodes a batch of 8 1.24$\times$ faster than P3-LLM-style on the edge server, at 1.39$\times$ less system
energy (Fig.~\ref{fig:e2e}). NPU + P3-LLM-style places each layer class on whichever unit runs it faster and reaches
1.03$\times$ NPU only's speed. On the mobile platform P3-LLM-style reaches 2.06$\times$ NPU only's speed, and CoDe
decodes 1.56$\times$ faster. CoDe pays for its speed with 0.59\,\% more of the stack's area: on the edge server CoDe
takes 1.35$\times$ P3-LLM-style's logic and returns 0.92$\times$ its tokens per second per logic mm$^2$, and on the
mobile platform 1.11$\times$.

\subsection{Energy and Peak Power}
\label{sec:eval:energy}

% P:eval-energy
\runin{Energy per token}
CoDe spends the least energy per token of the five systems on the mobile platform and ties for the least on the edge
server. On the mobile platform CoDe spends 106.0\,mJ per token at $M = 8$, while NPU only spends 6.0$\times$, stock AiM 1.93$\times$,
P3-LLM-style 1.38$\times$ and LP-Spec-style 1.12$\times$ CoDe's energy (Fig.~\ref{fig:e2e}c). On the edge server, CoDe spends 145\,mJ per token. NPU only spends
1.48$\times$, stock AiM 2.73$\times$ and P3-LLM-style 1.39$\times$ CoDe's energy, and CoDe matches LP-Spec-style's energy. With the idle NPU
power-gated, P3-LLM-style's ratio grows to 2.11$\times$: CoDe is fast enough to keep the linear layers in the banks,
while P3-LLM-style's NPU must read every linear-layer weight over the HBM pins.

% P:eval-power
\runin{Peak power}
PIM dies lift the stock die's \tfaw{} current limit so that all banks work at once: GDDR6-AiM's~\cite{aimjssc} all-bank
MACs draw about three times the gapless read current, and Newton's~\cite{newton} authors estimate about 4$\times$ the
power of a peak-bandwidth read. CoDe's peak power falls inside this headroom on both platforms and, with both designs' clocks gated, stays below
LP-Spec-style's. CoDe draws 0.51\,W per die at its full MAC rate, 1.14$\times$ the power of one x16 channel reading at its full
rate (Section~\ref{sec:method:models}), below the threefold read current of AiM's MACs. On HBM2, CoDe draws
5.76\,W per stack, 0.72$\times$ the stack's full-rate read power; HBM-PIM~\cite{hbmpim} likewise keeps its PIM mode within the thermal design power of the original
HBM system. CoDe draws 0.92$\times$ LP-Spec-style's peak power on the mobile platform and 0.87$\times$ on HBM2, and
1.09$\times$ and 1.00$\times$ with neither design gated (Table~\ref{tab:designs}).

\subsection{Area Against Silicon Budgets}
\label{sec:eval:area}

% P:eval-area-budget
Fabricated PIM dies set the scale for a PIM design's logic area, which a DRAM die pays for in memory capacity
(Section~\ref{sec:bg:walls}). Samsung's HBM-PIM~\cite{hbmpim} places 32 PIM units
of 0.712\,mm$^2$ each on an 84.4\,mm$^2$ die, 27\,\% of the die by our division. CoDe's logic (Table~\ref{tab:designs}) takes
2.64\,\% of the LPDDR5 die and 2.28\,\% of the HBM2 stack, against AiM's 20--25\,\%. Like AiM, CoDe keeps every cell array and places its PUs in the bank
periphery.

% P:eval-area-split
\runin{Logic against LP-Spec-style}
CoDe matches LP-Spec-style's peak throughput on the mobile platform with 0.574$\times$ its logic area per die: arithmetic takes
0.71 of LP-Spec-style's logic and 0.31 of CoDe's, while storage, the staging queue, accumulator file and weight latch,
takes 0.39 of CoDe's logic and 0.14 of LP-Spec-style's. On HBM2, CoDe's logic is 0.554$\times$ LP-Spec-style's and
1.35$\times$ P3-LLM-style's, 0.59\,\% more of the stack, an area that buys twice P3-LLM-style's beats per column period.

\runin{Sources of CoDe's gain}
CoDe's gain over stock AiM has two sources, row reuse and beat filling. Table~\ref{tab:umac_src} adds the two sources with row reuse first for one decoder layer's weight GEMMs at $M = 8$, the layer of Table~\ref{tab:umac} on the mobile platform. The row-reuse-only design keeps the stock PU's pace of one beat per column
period and adds CoDe's storage and row sweeps of $V$ tokens; we simulate it as CoDe's trace at $D = 1$, which reads
each weight column of the layer once, as CoDe does: one eighth as often as stock AiM, a quarter as often as
P3-LLM-style and half as often as LP-Spec-style. Row reuse alone speeds
the layer up 1.24$\times$ on the mobile platform and 1.15$\times$ on the edge server, yet $U$ reaches 0.223 and
0.222, because \UMAC stays at 1/4. Beat filling then adds one beat per column period at each step, raising \UMAC to
0.50, 0.73 and 1.00, and its three steps
speed the layer up 3.49$\times$ on the mobile platform and 3.33$\times$ on the edge server, while CoDe's \fMAC of 0.779 and 0.739 stays
near stock AiM's 0.717 and 0.771. End to end, beat filling makes CoDe decode 2.03$\times$ faster than row reuse alone
in the speculative loop at $M = 8$ on the mobile platform and 2.29$\times$ faster at a batch of 8 on the edge server. If DRAM silicon reaches only half of CK, CoDe at $D = 2$ still
returns 1.39$\times$ and 1.26$\times$ LP-Spec-style's tokens per second per logic mm$^2$ on the mobile platform and the edge server.
Row reuse raises the speedup that beat filling gives. Applied alone, it would shorten every MAC slot to a quarter but keep every
row-switch command, which would then take about half of the time or more (\fMAC 0.425 and 0.506), so beat filling
alone would reach only 2.37$\times$ and 2.62$\times$ stock AiM's speed.

% P:eval-vsweep-gain
\runin{Tile size on a full GEMM}
Fig.~\ref{fig:vsweep}a sweeps the tile size $V$ from 1 to 64 for q\_proj at $M = 64$, where every tile is full. With $D = 4$ PU beats per column period (Section~\ref{sec:bg:pim}), up to $V = D$ a larger
tile fills idle beats, and beyond
$V = D$ it removes only row-switch commands. CoDe's q\_proj speed-up over stock AiM rises from 1 at $V = 1$ to
3.86$\times$ on the mobile platform and 3.69$\times$ on the edge server at $V = D$, but only to 4.90$\times$ and
4.39$\times$ at $V = 64$. On the mobile platform idle beats supply 72\,\% of the time saved from $V = 1$ to 2, and
row-switch commands 91.6\,\% of that from $V = 4$ to 8.

% P:eval-vsweep-area
Past $V = D$ ($D = 4$) CoDe's storage grows faster than its speed. From $V = 4$ to 8 CoDe's logic grows by 19\,\% on the
mobile platform and by 45\,\% on the edge server, while its speed grows 1.117$\times$ and 1.089$\times$, so
throughput per logic mm$^2$ peaks at $V = D$ on both platforms, at 2.89$\times$ and 2.28$\times$ stock AiM's, and falls to 1.51$\times$ and 0.34$\times$ at $V = 64$
(Fig.~\ref{fig:vsweep}a). A full tile thus favours $V = D$, but a decode step runs at small $M$, where the last row
sweep of a tile is often only partly filled.

% P:eval-vsweep-choice
\runin{Tile size across {\boldmath$M$}}
CoDe uses $V = 8$ on the mobile platform and $V = 4$ on the edge server, the tile size that loses least in its worst
case across $M = 3$--16. Fig.~\ref{fig:vsweep}b divides $V = 8$'s decode-step throughput per logic mm$^2$ by $V = 4$'s. On the
mobile platform, $V = 8$ wins where it saves $V = 4$ a partly filled row sweep, at $M = 5$--7, 9--10 and 13--14
(1.290$\times$ at $M = 5$), and loses at $M \le 4$, where both tiles run one row sweep (0.840$\times$); against the
best $V$ at each $M$, $V = 8$ loses at most 16.0\,\%, while $V = 4$ loses 27.5\,\% on q\_proj. On the edge server, $V = 8$ never
breaks even (0.690--0.915$\times$), and $V = 4$ loses at most 8.9\,\% against $V = 8$'s 31.0--32.2\,\%.

% P:eval-placement
\runin{PU placement}
CoDe keeps its lead when one unit is shared between two banks, the other placement commercial PIM uses
(Section~\ref{sec:bg:pim}). Sharing costs speed only if a bank delivers a column as often as a unit takes one. On the
edge server a bank delivers one every 8\,ns and a PU takes one every 4\,ns (Table~\ref{tab:params}), so every design
there already shares one PU between two banks at full speed. On the mobile platform a bank delivers one every 5\,ns, as
fast as a unit takes one, so a shared unit halves each bank's rate: shared, LP-Spec-style takes 0.90$\times$ CoDe's
logic, and CoDe decodes 1.60$\times$ faster at $M = 8$ and returns 1.44$\times$ its tokens per second per logic mm$^2$.
