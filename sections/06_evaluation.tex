\section{Evaluation}
\label{sec:eval}

% P:eval-modelled
All results are modelled, on one DRAM timing per platform (Table~\ref{tab:params}) and one area model with one
tenfold DRAM-process factor for every design (Section~\ref{sec:method:models}); the LP-Spec-style variants of
Section~\ref{sec:eval:e2e} run on the mobile platform only, and ratios above 1 favour CoDe.

\subsection{Skinny GEMM Speedup and Area Efficiency}
\label{sec:eval:gemm}

% P:eval-gemm-summary
CoDe matches LP-Spec-style's GEMM speed on about half its logic and outruns P3-LLM-style once a GEMM has more than two
token rows. Fig.~\ref{fig:gemm} plots GEMM speed-up over stock AiM and throughput per logic mm$^2$ against $M$, each
point a geometric mean over the FC shapes of Section~\ref{sec:method:work}.

% P:eval-gemm-speed
\paragraph{GEMM speed}
Up to $M = 2$ the column period paces every design: one column read serves every token, and P3-LLM-style,
LP-Spec-style and CoDe all run 1.96--1.97$\times$ faster than stock AiM at $M = 2$ (Fig.~\ref{fig:gemm}a). Beyond
$M = 2$ P3-LLM-style needs a second pass for the tokens beyond its two per read, while CoDe fills up to four beats per
command: at $M = D = 4$ CoDe runs 3.74$\times$ stock AiM's speed on the mobile platform and 3.82$\times$ on the edge
server, against P3-LLM-style's 1.95$\times$. LP-Spec-style also fills four beats per column period, with four times
the multipliers, so its curve coincides with CoDe's up to $M = 4$, and at every $M$ on the edge server, where CoDe's
tile of $V = D = 4$ issues LP-Spec-style's command stream. On the mobile platform CoDe's eight-token tile halves
LP-Spec-style's row sweeps from $M = 8$, a lead of the tile size, not of decoupling (Section~\ref{sec:eval:e2e}).

% P:eval-gemm-per-mm2
\paragraph{GEMM throughput per logic mm$^2$}
Per logic mm$^2$, CoDe nearly doubles LP-Spec-style's GEMM throughput on both platforms. CoDe fills the same beats as
LP-Spec-style but spends its logic on storage rather than multipliers, so it reaches LP-Spec-style's speed with
0.539$\times$ its logic area on the mobile platform and 0.56$\times$ on the edge server
(Table~\ref{tab:designs}; Section~\ref{sec:eval:area}). CoDe therefore returns 1.86$\times$ LP-Spec-style's GEMM throughput per logic
mm$^2$ on the mobile platform up to $M = 4$ and 2.07$\times$ from $M = 8$; on the edge server the ratio is
1.79$\times$ at every $M$ (Fig.~\ref{fig:gemm}b). Against P3-LLM-style, CoDe's speed outgrows its larger logic
beyond $M = 2$: CoDe returns 1.43$\times$ P3-LLM-style's throughput per logic mm$^2$ at $M = 4$ and 1.59$\times$ from
$M = 8$ on the mobile platform, and 1.46--1.47$\times$ from $M = 4$ on the edge server. Only at $M \le 2$, where CoDe's
third and fourth beats sit idle, does P3-LLM-style's smaller PU lead, with CoDe at 0.75$\times$.

\subsection{End-to-End Speedup and Area Efficiency}
\label{sec:eval:e2e}

% P:eval-e2e-phone
\paragraph{Mobile platform}
Fig.~\ref{fig:e2e} runs whole decoding on the five systems of Section~\ref{sec:method:work}: the speculative loop at
$M = 4$ on the mobile platform and a batch of 8 on the edge server. At acceptance rate 0.7 a round of the loop yields
fewer than $1/(1 - 0.7) \approx 3.3$ tokens on average, so the verify pass stays short, and $M = 4$ is NPU only's
best $M$ and within 2\,\% of NPU + LP-Spec-style's and NPU + CoDe's best throughput; a batch of 8 is a light edge-server
load and the largest power of two before NPU only overtakes CoDe. On the mobile platform CoDe and LP-Spec-style
decode fastest, 4.37$\times$ and 4.34$\times$ faster than NPU only, at 46.4 and 46.1 tokens/s
(Fig.~\ref{fig:e2e}a). P3-LLM-style reaches 2.96$\times$, because its two-token read needs two passes over the four
token rows, and stock AiM reaches 1.81$\times$. At each system's own best $M$ the order holds: CoDe reaches
47.1 tokens/s and LP-Spec-style 46.8 at $M = 3$, P3-LLM-style 43.8 and stock AiM 26.5 at $M = 2$, and NPU only 10.6
at $M = 4$.

% P:eval-e2e-server
\paragraph{Edge server}
On the edge server only CoDe and LP-Spec-style decode a batch of 8 faster than NPU only, both 1.28$\times$ at
456 tokens/s (Fig.~\ref{fig:e2e}a). Stock AiM runs at 0.45$\times$ and P3-LLM-style at 0.76$\times$ NPU only's speed,
so at the batch where P3-LLM~\cite{p3llm} moves its linear layers to the NPU, CoDe decodes 1.68$\times$ faster than
P3-LLM-style. On the geometric mean over the five models, NPU only overtakes CoDe from batch 16.

% P:eval-e2e-per-mm2
\paragraph{Throughput per logic mm$^2$}
At LP-Spec-style's decoding speed, CoDe returns 1.87$\times$ LP-Spec-style's tokens per second per logic mm$^2$ on the
mobile platform and 1.79$\times$ on the edge server (Fig.~\ref{fig:e2e}b), because CoDe needs about half its logic. Against P3-LLM-style, whose PU takes less logic than CoDe's, CoDe's speed lead more than repays the area:
CoDe returns 1.10$\times$ P3-LLM-style's decoding throughput per logic mm$^2$ on the mobile platform and 1.26$\times$ on the
edge server.

% P:eval-lpspec-variants
\paragraph{LP-Spec-style variants}
Neither LP-Spec's published sharing nor an eight-token tile closes CoDe's lead per logic mm$^2$ on the mobile
platform. Built as LP-Spec~\cite{lpspec} publishes it, with one unit shared between two banks, LP-Spec-style takes
0.96$\times$ CoDe's logic, 2.21\,\% of the die, but each unit reads one of its two banks per column period, half the
per-bank rate. CoDe thus decodes 1.49$\times$ faster at $M = 4$ and 1.60$\times$ at $M = 8$ and 16, and returns
1.42--1.45$\times$ the shared design's tokens per second per logic mm$^2$ (at $M = 4$ and at each design's best $M$).
The 1.49$\times$ holds on the 5\,ns all-bank column that every design shares; LP-Spec's own per-die throughput and
bandwidth imply a 10\,ns bank column, at which sharing loses nothing. With an eight-token tile, LP-Spec-style ties
CoDe's loop speed at every $M$ we run (2--4, 8 and 16) and CoDe's GEMM speed from $M = 8$ (1.007$\times$ at $M = 12$),
so the tile, not decoupling, gives CoDe its mobile speed lead over the per-bank LP-Spec-style beyond $M = 4$. The
eight-token tile, however, grows LP-Spec-style's logic to 4.72\,\% of the die, and CoDe returns 2.05$\times$ that
design's tokens per second per logic mm$^2$.

\subsection{Energy and Peak Power}
\label{sec:eval:energy}

% P:eval-energy
\paragraph{Energy per token}
CoDe spends the least energy per token of the five systems on both platforms. On the mobile platform the speculative
loop on CoDe spends 70.5\,mJ per token at $M = 4$, while NPU only spends 7.9$\times$, stock AiM 1.80$\times$,
P3-LLM-style 1.28$\times$ and LP-Spec-style 1.04$\times$ CoDe's energy (Fig.~\ref{fig:e2e}c). On the edge server,
with the NPU idling at 55\,W while the PIM works, NPU only spends 1.48$\times$ and P3-LLM-style 1.64$\times$ CoDe's
energy per token, and LP-Spec-style ties CoDe; with the idle NPU power-gated, P3-LLM-style still spends 1.46$\times$
CoDe's energy.

% P:eval-power-headroom
\paragraph{Power headroom of all-bank PIM}
A stock DRAM die holds its banks to a tight current limit: its \tfaw{} window admits only four row activations because
the die's charge pumps and their power-delivery network supply only that current~\cite{shevgoor}. PIM dies lift this
limit so that all their banks can work at once. GDDR6-AiM's~\cite{aimjssc} all-bank MACs draw about three times the
gapless read current, and reservoir capacitors and separate I/O and bank power networks let its 16 banks activate
together without \tfaw. AttAcc~\cite{attacc} budgets its GEMV units by the all-bank interleaved read current (IDD7),
Newton's~\cite{newton} authors estimate that its all-bank computation draws about 4$\times$ the power of a peak-bandwidth
read, and SK hynix~\cite{aimxhc36} lists the number of banks that run MACs among the power-throttling knobs of its
future AiM designs. CoDe's design operates within this headroom.

% P:eval-power
\paragraph{Peak power}
CoDe's peak power falls inside this headroom on both platforms and stays close to LP-Spec-style's. CoDe draws
0.54\,W per die at its full MAC rate, 1.20$\times$ the power of one x16 channel reading at its full
rate (Section~\ref{sec:method:models}), well below the threefold read current of AiM's MACs. On HBM2, CoDe draws
5.98\,W per stack, 0.75$\times$ the stack's full-rate read power, so CoDe's PUs fit within the read power an HBM2 stack
already delivers; HBM-PIM~\cite{hbmpim} likewise keeps its PIM mode within the thermal design power of the original
HBM system. CoDe draws 0.92$\times$ LP-Spec-style's peak power on the mobile platform and 0.87$\times$ on HBM2, and
even without its clock gates CoDe draws only 1.04$\times$ and 1.03$\times$ LP-Spec-style's peak
(Table~\ref{tab:designs}). CoDe spreads its MAC rate over four times as many clock edges as LP-Spec-style,
so each CoDe edge draws 3.4$\times$ less charge on the mobile platform and 3.1$\times$ less on HBM2.

\subsection{Area Against Silicon Budgets}
\label{sec:eval:area}

% P:eval-area-budget
Fabricated PIM dies set the scale for a PIM design's logic area. Samsung's HBM-PIM~\cite{hbmpim} places 32 PIM units
of 0.712\,mm$^2$ each on an 84.4\,mm$^2$ die, 27\,\% of the die by our division; GDDR6-AiM's compute circuits take 20--25\,\% of its chip (Section~\ref{sec:bg:walls}). CoDe's logic takes
2.31\,\% of the LPDDR5 die and 1.95\,\% of the HBM2 stack (Table~\ref{tab:designs}), and 4.96\,\% and 4.02\,\% at AiM's
silicon scale, at most a quarter of AiM's share. Like AiM, CoDe keeps every cell array and places its PUs in the bank
periphery. LP-Spec-style's logic takes 4.28\,\% of the die and 3.48\,\% of the stack, and 9.47\,\% and 7.50\,\% at
silicon scale.

% P:eval-area-split
\paragraph{Logic against LP-Spec-style}
CoDe reaches LP-Spec-style's peak on the mobile platform with 0.539$\times$ its logic area per die: arithmetic takes
0.73 of LP-Spec-style's logic and 0.34 of CoDe's, while storage, the staging queue, accumulator file and weight latch,
takes 0.32 of CoDe's logic and 0.10 of LP-Spec-style's. On HBM2, CoDe's logic is 0.56$\times$ LP-Spec-style's and
1.33$\times$ P3-LLM-style's, an area that buys twice P3-LLM-style's beats per column period.

\subsection{Ablation Study}
\label{sec:eval:ablation}

% P:eval-gain-sources
\paragraph{Sources of CoDe's gain}
CoDe's gain over stock AiM has two sources, row reuse and beat filling. Table~\ref{tab:umac_src} adds the two sources with row reuse first for one decoder layer's weight GEMMs at $M = 8$, the layer of Table~\ref{tab:umac} on the mobile platform and
of Llama-3.1-8B on the edge server. The row-reuse-only design keeps the stock PU's pace of one beat per column
period and adds CoDe's storage and row sweeps of $V$ tokens; we simulate it as CoDe's trace at $D = 1$. Row reuse alone speeds
the layer up 1.24$\times$ on the mobile platform and 1.15$\times$ on the edge server, yet $U$ reaches only 0.223 and
0.222, because \UMAC stays at 1/4.
Beat filling then fills the idle beats and supplies the large step,
3.49$\times$ on the mobile platform and 3.33$\times$ on the edge server, while CoDe's \fMAC of 0.779 and 0.739 stays
near stock AiM's 0.717 and 0.771. In the other order, modelled as a quarter of stock AiM's MAC slots plus its non-MAC time per row sweep, beat filling
alone would cut \fMAC, and with \UMAC at 1 also $U$, to 0.425 and 0.506, in steps of 2.37$\times$ then 1.83$\times$ on
the mobile platform and 2.62$\times$ then 1.46$\times$ on the edge server, because the unchanged non-MAC commands would
take about half of the shortened time or more. Beat filling thus earns its full step only
once row reuse has removed most of the row-switch overhead per token.

% P:eval-vsweep-gain
\paragraph{Tile size on a full GEMM}
Fig.~\ref{fig:vsweep}a sweeps the tile size $V$ from 1 to 64 for q\_proj at $M = 64$, where every tile is full; the
mobile staging is a register of $V$ slices below $V = 8$. Up to $V = D$ a larger tile fills idle beats, and beyond
$V = D$ it removes only row-switch commands. CoDe's q\_proj speed-up over stock AiM rises from 1 at $V = 1$ to
3.86$\times$ on the mobile platform and 3.69$\times$ on the edge server at $V = D$, but only to 4.90$\times$ and
4.39$\times$ at $V = 64$. On the mobile platform idle beats supply 72\,\% of the time saved from $V = 1$ to 2, and
row-switch commands 91.6\,\% of that from $V = 4$ to 8.

% P:eval-vsweep-area
Past $V = D$ CoDe's storage grows faster than its speed. From $V = 4$ to 8 CoDe's logic grows by 16\,\% on the
mobile platform and by 40\,\% on the edge server, while its speed grows only 1.117$\times$ and 1.089$\times$, so
throughput per logic mm$^2$ peaks at $V = D$ on both platforms, at 3.01$\times$ and 2.34$\times$ stock AiM's
(Fig.~\ref{fig:vsweep}a). A full tile thus favours $V = D$, but a decode step runs at small $M$, where the last row
sweep of a tile is often only partly filled.

% P:eval-vsweep-partial
\paragraph{Tile size across $M$}
Fig.~\ref{fig:vsweep}b sets $V = 8$ against $V = 4$ in a decode step's throughput per logic mm$^2$ for $M = 1$--16.
$V = 8$ wins only where
it saves $V = 4$ a partly filled row sweep, and loses where both tiles run the same row sweeps. At $M = 5$, $V = 4$
runs two row sweeps of three and two tokens where $V = 8$ runs one, and $V = 8$ returns 1.324$\times$ $V = 4$'s
throughput per mm$^2$; on the mobile platform $V = 8$ wins at $M = 5$--7, 9--10 and 13--15. Up to $M = 4$ both
tiles run one row sweep, and $V = 8$ returns 0.862$\times$. On the edge server $V = 8$ never breaks even and returns
at best 0.944$\times$.

% P:eval-vsweep-choice
CoDe sets $V$ per platform by the worst loss in throughput per logic mm$^2$ across $M = 3$--16, against the best of
$V = 2$, 4, 8 and 16 at each $M$. On the mobile platform $V = 8$ loses at most 13.8\,\%, against $V = 4$'s
29.4\,\% on q\_proj, so CoDe sets $V = 8$. On the edge server $V = 4$ loses at most 11.7\,\% and $V = 8$ 28.8--30.0\,\%, so CoDe sets $V = 4$.
The mobile $V = 8$ pays its worst loss at $M = 3$--4, which includes the $M = 4$ of Section~\ref{sec:eval:e2e}, the
loop's best $M$ with an EAGLE head.
